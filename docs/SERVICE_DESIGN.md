# 가전 구매 청문회 — 서비스 설계 v0.2

작성: 2026-10-29 (v0.1) · 갱신: 2026-10-30 (v0.2, 인계 문서 반영)

상태: 기획·설계 문서. 사용자 조사·성능 검증·개발 완료를 의미하지 않는다. 우선순위는 [MOSCOW.md](MOSCOW.md), 실제 진행 상태는 [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md)를 본다.

- 서비스명: 가칭 **가전 구매 판단 시뮬레이터**. 화면의 **BEFORE**는 임시 브랜드이며 최종 이름이 아니다.
- 별개 프로젝트: Money_to_Home 등 다른 프로젝트의 코드·보고 내용을 섞지 않는다.

## 1. 한 문장과 목표

사용자가 가져온 가전제품 정보와 구매 이유를 바탕으로 사용 상황 세 가지와 근거 있는 찬반 청문회를 보여주고, 사용자가 자신의 구매 여부를 결정하도록 돕는 웹 서비스.

사용자의 최종 목표(셋 중 하나를 스스로 설명할 수 있게):

- 이런 단점이 있어도 내게 중요한 편익 때문에 **구매**한다.
- 이런 장점이 있어도 감수하기 어려운 제약 때문에 **구매하지 않는다**.
- 아직 확인할 조건이 있어 **추가로 조사**한다.

AI는 승자·임의 점수·구매 명령을 내지 않는다. 성공 기준은 구매율이 아니라 사용자가 근거와 불확실성을 이해하고 자기 결정을 설명할 수 있는지다.

목표가 아닌 것: 구매 전환 극대화, AI의 구매 판결, 실제 제품 성능의 물리적 재현.

## 2. 문제·사용자 — 검증할 가설

- 문제 가설: 사양과 장단점을 읽어도 자기 생활에서 생길 이점·불편으로 연결하기 어렵고, 어떤 단점을 감수할지 판단하기 어렵다.
- 대표 사용자 가설: 특정 제품을 이미 골랐지만 설치·관리 부담과 기대 편익을 자기 생활 기준으로 점검하고 싶은 소비자.
- 인터뷰를 아직 수행하지 않았다. Persona·문제 정의를 조사 결과처럼 쓰지 않는다.
- 초기 조사 제안: 최근 가전을 고민·구매한 사람 5명 내외. 질문: 구매 계기 / 가장 어려운 판단 / 확인한 자료 / 예상 못한 불편 / 무엇을 알았다면 선택이 달라졌을지. 결과는 수행 일시·질문·관찰만 실제로 기록한다.

- 캐릭터 직접 조작과 도트 배치는 흐름에 넣지 않는다. 일반 웹 UI(다음/뒤로/근거 펼치기)와 게임 조작을 구분한다.
- PC: 도트와 설명/근거를 좌우 배치. 모바일: 세로 배치. 도트 비율 유지, 본문 글자를 이미지에 박지 않는다.
- 처음 시작은 로그인 없이.

### 3.1 시안에서 그대로 가져갈 원칙

- 조건 카드의 세 가지 태그 — **사용자 입력 / 가정 / 확인 필요** — 를 모든 화면에서 같은 의미로 쓴다.
- 제품 확인: ‘정보가 없는 항목은 추측하지 않아요’ — 값 없으면 ‘확인 필요’로 둔다.
- 상황: ‘제품 성능을 재현한 영상이 아닌 가상 상황이에요’ 고지.
- 청문회: 주장 수정 카드(예: ‘정리 부담은 남지만 이 사용자에게 결정적 단점에서는 제외’) — 제품 사실은 그대로, 사용자에게 주는 중요도만 바뀜.
- 결과: 세 열(사용자 기대 / 조건에 따라 달라짐 / 자료 확인 필요)과 세 선택지.

### 3.2 시안과 다르게 구현하는 부분 (2026-10-30 확정, [MOSCOW.md §3](MOSCOW.md))

- 상황 화면: 자동 재생 + 상황 이동·건너뛰기 + ‘움직임 멈추기’. 일시정지·다시보기·타임라인·전체화면은 넣지 않음(S).
- 결과 화면: ‘선택 기록하기’ → ‘내 결정 정리’. 탭 안 요약 + 클립보드 복사. 서버 저장 없음.
- 헤더: 북마크·통계·설정 아이콘 제외. 로고 + 이용 방법 + 예시 체험.
- 제품 확인 ‘원문 보기’: 사용자가 붙여넣은 원문(예시 제품은 검수한 예시 자료)만. 외부 URL 생성 금지. 시안의 날짜·인물 이름 등은 자리표시 텍스트다.

## 5. 비기능 요구사항 — 초기 목표

- API 키는 서버 환경변수로만. 프론트 번들·로그·저장소에 넣지 않는다.
- 생성 중 진행 상태·재시도 제공. 호출 제한·타임아웃 설정.
- JSON 형식뿐 아니라 허용 자산·소품·효과·참조 ID·사양 근거를 서버에서 검증.
- 외부 제품 페이지·붙여넣기 자료는 데이터. 그 안의 문구가 진행 규칙을 바꾸지 못하게 (J07=M).
- 반응형(N02=M). 기본 label·키보드·초점 처리. 움직임을 줄이거나 멈출 수 있게.
- 지연·오류율·토큰 사용량을 측정. 수치 목표는 실측 후 확정. 측정 안 한 목표를 달성했다고 쓰지 않는다.
- 불필요한 개인정보를 요구하지 않는다. 데이터는 현재 탭 상태까지만 (영구 저장은 W).

## 6. 도트 표현

### 6.1 의미

도트는 **상황 이해를 돕는 예시 장면**이다. 실제 집 구조·축척·성능을 재현한다고 주장하지 않는다. 화면에 ‘사용 상황 예시 · 실제 구조·축척과 다름’ 같은 짧은 문구를 둔다. 예시라는 표시가 근거 없는 스펙·성능을 만들어도 된다는 뜻은 아니다.

예: ‘집 20평, 바닥에 물건 많음, 청소 시간 줄이고 싶음’ 입력 →
1. 기본 거실 배경에 준비된 전선·장난감 소품과 청소기 배치
2. 설명 카드에 ‘사용자 입력: 집 20평 / 바닥 물건 많음’
3. 청문회는 청소 편익과 사전 정리 부담을 논의
4. 도트 방이 실제 20평이거나 실제 청소 범위·성능이라고 설명하지 않음

집 전체 면적만 들었으면 방별 면적·가구 배치를 추론하지 않는다. 미확인 조건은 가정/미확인으로, 표현할 자산이 없는 조건은 글로 설명한다.

### 6.2 표현 매핑

| 입력·판단 정보 | 시각 표현 | 텍스트 처리 |
|---|---|---|
| 집 크기 | 고정된 기본 공간 | 입력 면적과 ‘사용자 입력’ 출처 표시 |
| 바닥 물건 많음 | 허용된 clutter 소품 켜기 | 사전 정리 부담을 조건부로 설명 |
| 퇴근 후 사용 | 저녁 톤 또는 시간 아이콘 | 사용 목적과 기대 편익 연결 |
| 관리 작업 | 필터·먼지통 등 상태 변화 | 해당 모델에서 확인한 관리 내용만 |
| 설치 공간 부족 가능성 | 제품 + 공간 확인 표시 | 확인된 치수와 필요한 확인 사항. 실측 배치 검증처럼 표현하지 않음 |
| 재현하기 어려운 조건 | 제품군 기본 장면 | 조건과 한계를 설명 카드에 |

### 6.3 구성 요소

고정 배경 + 선택 가능한 소수 소품(ON/OFF) + 제품의 단순 작동/상태 효과 + 설명 카드.

- 인물은 정적이어도 된다. 공통 보행·정리·적재 캐릭터 엔진은 필수가 아니다.
- 제품 움직임: 청소기 정해진 경로 이동, 작동 표시, 먼지통/필터 상태 등 준비된 간단한 효과.
- 공통 공간 3개(거실 / 주방 / 세탁 공간)를 제품군끼리 재사용.
- 대형 게임 엔진은 필수 도입하지 않는다. CSS 또는 Canvas 중 한 가지 방식을 고른다.

## 7. AI·근거·실패 처리

### 7.1 흐름

제품 근거 + 구매 이유 → 장면 계획(JSON) → 서버 검증 → 도트 재생 → 찬성 주장 → 반대 반문 → 응답·수정 → 다음 상황.

AI는 준비된 장면·소품·효과의 **허용 ID만 고른다**. 임의 코드·자산 경로를 만들어 실행하지 않는다.

### 7.2 장면 계획 필드 (초안 — 구현 시 확정해 이 문서에 기록)

```json
{
  "scene_id": "rv_clutter",
  "condition_refs": ["cond_floor_items"],
  "assumptions": ["바닥에 작은 물건이 놓인 경우"],
  "prop_ids": ["cable", "socks"],
  "effect_ids": ["warning_mark"],
  "caption": "바닥에 작은 물건이 놓여 있는 경우를 살펴봐요.",
  "claim_refs": ["c_pro_1", "c_con_1"],
  "source_refs": []
}
```

서버는 제품군·장면·소품·효과의 허용값과 조합을 검사한다. 구현에 없는 자산을 참조하면 제품군 기본 장면으로 대체(F10). 위 예처럼 자료가 없는 조건부 장면은 실제 제품의 장애물 대응 실패를 표현하지 않는다.

### 7.3 청문회 규칙

- 찬성: 구매 목적과 연결된 편익을 근거로.
- 반대: 사용자 조건에서 중요한 불편·제약을 근거로.
- 반문: 상대가 제시한 전제와 근거를 다룬다(이전 주장 ID 지정).
- 후속 응답: 유지·수정·철회를 드러낸다. 새 정보가 없으면 억지로 입장을 바꾸지 않는다.
- 철회 장면을 연출하려고 일부러 틀린 주장을 만들지 않는다. 정보가 부족하면 ‘확인 불가’.
- 장면 3개, 발언 수·길이 상한. 추가 질문 최대 1개·건너뛰기 가능.
- 대화 중 수정은 검토 상태의 갱신이다. 모델이 실시간 재학습한다고 말하지 않는다.
- 같은 모델의 재검토를 독립 사실 검증으로 표현하지 않는다. 상대 AI 발언은 제품 근거가 아니다.

### 7.4 자료와 Hallucination 방지

- 제품 사실 / 사용자 진술 / AI 해석·가정 / 미확인을 구분한다.
- 확인되지 않은 기능·소음·절약 시간·전기료·확률·성능 수치를 만들지 않는다. 숫자 계산은 입력과 산식을 보인다.
- 자료에 없는 출처 URL을 만들지 않는다. 붙여넣기 자료는 ‘사용자 제공 자료’로 구분.
- 모델을 특정할 수 없으면 사용자에게 모델·자료 확인을 요청한다. 제품명만으로 기억 속 사양을 사실처럼 채우지 않는다.
- 사용자가 제품 정보와 가정을 수정하면 관련 장면·주장에 반영된다 (Human-in-the-loop). 최종 결정은 사용자.

### 7.5 실패 구분

| 실패 | 처리 |
|---|---|
| 링크 본문 읽기 실패 | 사유 안내 → 스펙 텍스트/직접 입력/예시로 이어감 |
| 자료 부족·모델 불일치 | 미확인·추가 확인 필요 표시. 추정 스펙 생성 금지 |
| AI 응답 실패·한도 소진 | 입력 보존, 제한된 재시도/실패 안내. 예시 모드는 예시라고 표시 |
| 맞춤 도트 구성 실패 | 제품군 기본 장면 + ‘기본 사용 장면’ 표시 |
| 전체 분석 실패 | 기본 도트를 띄우더라도 정상 분석 결과처럼 꾸미지 않음 |

링크 수집을 만들면 지원 사이트·URL 유형을 좁히고 URL 읽기 보호를 함께 적용한다. ‘링크 입력 지원’과 ‘모든 링크 자동 분석’을 혼동하지 않는다.

## 8. 기술 구성

| 영역 | 현재 | 상태 |
|---|---|---|
| 프론트 | React 19 + TypeScript + Vite 8 | 뼈대 구성·빌드 확인 |
| 스타일 | 일반 CSS, Grid/Flex + 미디어 쿼리 | CSS 프레임워크(Bootstrap 등) 쓰지 않기로 함 |
| 백엔드 | Python 3.12 + FastAPI (uv) | `/api/health`만 구현 |
| AI | Gemini API 단일 모델 | 미연동. 모델 ID·한도는 공식 문서·계정으로 확인 후 기록 |
| 도트 | 고정 자산 + CSS/Canvas 상태 효과 | 미착수. 방식 미선택 |
| 데이터 | 제품/출처/장면 설정 파일 + 현재 탭 상태 | DB·회원 없음 |
| 배포 | 미정 | 배포·접속 검증 후 기록 |

예시(mock)/실제(live) 모드: 서버 `APP_MODE=live`이고 키가 있을 때만 실제 모드. 화면에 모드를 항상 표시하고 예시 응답을 실제 AI 생성처럼 보이지 않게 한다.

## 9. UT 계획과 성과지표

실제 구매 고민이 있는 5명 내외 소규모 탐색. 단일 집단 결과를 일반화하지 않는다.

과업: 제품·구매 이유 입력 → 상황 확인 → 근거 확인 → 질문 답변 또는 건너뛰기 → 결정 이유 설명.

| 지표 | 측정 정의 |
|---|---|
| 과업 완료율 | 도움 없이 최종 선택까지 도달한 인원 / 시작 인원 |
| 이해도 | 핵심 이득·불편·미확인을 자기 말로 설명하는지 |
| 사실/예상 구분 | 예시 주장을 올바르게 분류하는지 |
| 결정 도움 | 전후 이유의 구체성 + 주관적 도움 평가 |
| 근거 정확성 | 검토한 제품 사실 주장 중 자료로 지지되는 비율 |
| 주장 갱신 적절성 | 조건 변경 시 관련 주장만 타당하게 바뀌는지 |
| 부담 | 질문 이탈·건너뛰기, 긴 대사 관찰 |
| 운영 | 응답 지연·오류율·호출량 |

구매율 상승·토론 승률은 핵심 지표가 아니다. ‘프로그램이 실행됨’, ‘시안이 완성됨’, ‘사용자가 도움을 받음’은 서로 다른 검증 결과다.

## 11. 구현 순서

1. 4개 제품군의 검증된 예시와 5개 화면을 연결 (키 없는 예시 모드).

6. 4개 제품군 정상 사례 + 잘못된 입력·자료 부족·AI 실패·장면 실패 사례 확인.
7. 실제 대상 사용자 UT, 이해한 근거와 불편 기록.
8. 실제 상태로 보고서 6개 항목·기술스택·GitHub 주소 갱신.

## 12. 미확정 사항

도트 구현 방식(CSS/Canvas)·시점·캐릭터 비율, 최종 서비스명, 링크 지원 사이트, Gemini 모델 ID와 실제 한도, 근거 자료 확보 방식, 배포 호스팅. 무료 API의 존재만으로 공개 서비스의 무제한 운영을 보장하지 않는다.
