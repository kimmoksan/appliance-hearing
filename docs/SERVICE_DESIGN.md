# 가전 구매 청문회 — AX 서비스 설계 초안 v0.1

작성일: 2026-10-29

상태: 기획 초안. 사용자 조사·성능 검증·개발 완료를 의미하지 않는다. 제품군 4종은 현재 제안 범위이며 최종 확정 전이다.

## 1. 문제 → 사용자 → 해결 → 효과 → 검증

- 문제 가설: 구매 후보 가전은 있지만 사양과 장단점이 자기 생활에 어떤 의미인지 판단하기 어렵다.
- 대상: 구매 후보가 있고 구매 이유는 있으나 감수할 불편을 정리하지 못한 소비자.
- 해결: 제품 자료와 짧은 구매 이유를 받아 도트 상황을 구성하고, 근거를 연결한 찬반 반문을 제공한다.
- 기대 효과 가설: 사용자가 기대 이득·감수할 불편·미확인 정보를 구분하고 자기 기준으로 결정한다.
- 검증: 이용 전후 이유 설명, 사실/가정 구분, 과업 완료, 근거 오류 검토.
- 목표가 아닌 것: 구매 전환 극대화, AI의 구매 판결, 실제 제품 성능의 물리적 재현.

## 2. 사용자 조사와 Persona

가설 Persona: 후보 제품을 정한 소비자. 리뷰를 많이 읽지만 설치·관리·일상 사용에 적용하기 어려워 결정을 미룬다. 구매 이유는 시간 절약·편리함·감성 등 다양하며 정당성은 AI가 임의로 정하지 않는다.

초기 조사 제안: 최근 가전을 고민하거나 구매한 사람 5명 내외. 대표성 있는 통계 조사로 해석하지 않는다.

질문: 구매 계기 / 가장 어려운 판단 / 확인한 자료 / 예상 못한 불편 / 무엇을 알았다면 선택이 달라졌을지.

조사 결과에 따라 Persona와 상황 우선순위를 수정한다. 인터뷰 결과를 만들어 쓰지 않는다.

## 3. User Journey

| 단계 | 사용자 행동·생각 | 서비스 동작 | 마찰 관리 |
|---|---|---|---|
| 시작 | 이 제품이 나에게 맞을까? | 지원 제품군과 입력 안내 | 로그인 없이 시작 제안 |
| 입력 | 링크 또는 자료 + 구매 이유 한 줄 | 추출·정리, 누락 확인 | 링크 실패 시 텍스트 대체 |
| 확인 | 제품 정보가 맞는가? | 간단한 정보 확인 카드 | 장문의 사전 설문 없음 |
| 상황 | 내 생활에서도 이럴까? | 기본 상황 3개에 요소·행동 조합 | 사용자 미제공 조건은 가정 표시 |
| 청문 | 이 주장에 근거가 있나? | 주장 → 반문 → 답변·수정 | 짧은 발언, 근거 펼쳐보기 |
| 개입 | 이 부분은 내 상황과 다름 | 필요할 때 선택형 질문 | 생략 가능, 첫 버전 최대 1회 제안 |
| 결정 | 이 불편을 감수할까? | 이득·불편·미확인 정보 정리 | 구매/비구매/더 알아보기 |

## 5. 비기능 요구사항 — 초기 검증 목표

- API 키는 서버 환경변수로만 관리하고 프론트 번들·로그·저장소에 포함하지 않는다.
- 생성 중 진행 상태와 재시도를 제공한다. 호출 제한·타임아웃 정책을 설정한다.
- JSON 형식뿐 아니라 허용 자산·행동·좌표 슬롯·참조 ID·사양 근거를 서버에서 검증한다.
- 외부 제품 페이지는 데이터로 취급한다. 페이지 문구가 시스템 역할·도구 실행을 바꾸지 못하게 한다.
- 애니메이션을 보지 않아도 상황·근거를 읽을 수 있고 움직임을 줄이거나 중단할 수 있다.
- API 지연·오류율·사용 토큰을 측정한다. 응답 시간 수치 목표는 실측 후 확정한다.
- 시연용 입력은 불필요한 개인정보를 요구하지 않는다. 기록 보관 범위와 삭제 정책은 공개 MVP 전 확정한다.

## 6. MoSCoW

| 우선순위 | 범위 |
|---|---|
| Must | 4종용 장면 체계, 직접 입력, 구매 이유, 조립형 상황, 짧은 공방, 근거 표시, 선택적 개입, 사용자 결정 |
| Should | 지원 사이트 링크 추출, 변경 전후 비교, 재생 기록 |
| Could | 음성, 꾸미기, 공유, 회원별 기록 |
| Won't (이번 범위) | 모든 쇼핑몰·가전 지원, 생성 영상, 자유 이동 게임, 실제 성능 예측, 자동 구매, 무제한 토론 |

링크 입력 편의성은 중요하지만 추출 가능성은 사이트별 검증이 필요하다. 프로토타입에서는 준비된 자료를 사용할 수 있고 이를 실제 자동 추출로 오인시키지 않는다.

## 7. 도트 제작 원칙

완성 영상 12개를 고르는 방식이 아니다. 제품군별 기본 장면 3개에 사람·물건·제품 상태·행동 순서를 조합한다. 지원 가능한 동작 목록은 고정한다.

4종 전체를 목표로 하되 첫 개발은 한 장면을 끝까지 연결해 공통 재생기를 검증한 뒤 확장한다.

모든 동작을 새 스프라이트로 그리지 않는다. 이동·흔들림·점멸·회전·효과는 코드로 처리할 수 있다. 손동작 등 표현이 어려운 내용은 아이콘과 자막으로 대체한다. 도트 배치·속도·입자는 실제 크기·성능 측정값이 아니다.

## 9. AI 제어 구조

제품 근거 + 구매 이유 → 상황 계획(JSON) → 서버 검증 → 도트 재생 → 찬성 주장 → 반대 반문 → 답변·수정 → 다음 쟁점.

장면 데이터 예:

```json
{
  "scene_id": "floor_preparation",
  "room": "living_room",
  "assumptions": ["바닥에 작은 물건이 놓인 경우"],
  "objects": [{"asset_id": "small_items", "slot": "floor_a"}],
  "actions": [
    {"actor": "person", "action": "walk", "target": "floor_a"},
    {"actor": "person", "action": "handle_object", "target": "small_items"}
  ],
  "evidence_ids": [],
  "claim_type": "conditional_scenario"
}
```

자료가 없는 예시 장면이므로 실제 제품의 장애물 대응 실패를 표현하지 않는다. 행동은 화이트리스트 내에서만 실행하며 모델이 만든 코드를 실행하지 않는다.

반문은 이전 주장 ID를 지정한다. 새 정보가 없으면 억지로 입장을 바꾸지 않는다. 감수 의사는 제품 사실을 바꾸지 않고 사용자에게 단점의 중요도를 바꾼다. 첫 버전은 쟁점당 짧은 공방으로 제한한다.

## 10. Hallucination과 Human-in-the-loop

- 제조사 사양·설명서 등 확보한 자료와 사용자 답변을 근거로 사용한다. 링크 URL만 붙이고 검증했다고 처리하지 않는다.
- 사실 / 사용자 진술 / 조건부 예상 / 확인 필요를 구분한다.
- 숫자 계산이 있으면 입력과 산식을 표시한다. 없는 성능·유지비·시간을 생성하지 않는다.
- 사용자가 제품 정보와 가정을 수정할 수 있게 한다. 수정된 정보가 관련 장면·주장에 반영되어야 한다.
- 상대 AI의 발언은 제품 사실을 증명하는 독립 근거가 아니다.
- 최종 결정은 사용자에게 있다. 구매 판결이나 찬반 승률을 강제하지 않는다.

## 11. Wireframe과 Prototype 계획

| 화면 | 배치·동작 |
|---|---|
| 입력 | 서비스 설명, 지원 4종, 제품 입력, 구매 이유, 시작 버튼 |

| 선택 개입 | 논점 관련 짧은 질문과 선택지·건너뛰기 |
| 결과 | 얻는 것·감수할 것·추가 확인, 사용자 선택과 결정 이유 |

프로토타입: 준비된 사례로 클릭·재생·선택·화면 이동을 검증한다. 준비된 대사는 실제 AI 응답으로 표시하지 않는다.

MVP: 실제 AI와 서버 검증을 연결하고, 지원 4종에서 사용자 입력이 장면 구성·발언에 반영되는지 확인한다.

## 12. UT 계획과 성과지표

초기 UT 제안: 실제 구매 고민이 있는 5명 내외의 소규모 탐색. 단일 집단 결과를 시장 전체로 일반화하지 않는다.

과업: 제품·구매 이유 입력 → 상황 확인 → 근거 확인 → 선택 또는 건너뛰기 → 결정 이유 설명.

| 지표 | 측정 정의 |
|---|---|
| 과업 완료율 | 도움 없이 최종 선택까지 도달한 인원 / 시작 인원 |
| 이해도 | 핵심 이득·불편·미확인 사항을 자기 말로 설명하는지 |
| 사실/예상 구분 | 예시 주장들을 올바르게 분류하는지 |
| 결정 도움 | 전후 이유의 구체성 + 주관적 도움 평가 |
| 근거 정확성 | 검토한 제품 사실 주장 중 자료로 지지되는 주장 비율 |
| 주장 갱신 적절성 | 조건 변경 테스트에서 관련 주장만 타당하게 바뀌는지 |
| 부담 | 질문 단계 이탈·건너뛰기, 긴 대사에 대한 관찰 |
| 운영 | 응답 지연·오류율·호출량 |

구매율 상승·토론 승률은 핵심 성과지표로 삼지 않는다. 만족도만으로 정확성을 입증하지 않는다. 자유 답변 정확성과 프레임 렌더링 성능은 별도 검증한다.

## 13. 개발 순서·역할

1. 피터: 화풍·시점·화면 경험 선택, 사용자 조사, 지원 4종 확정.
2. 함께: 제품별 검증 자료와 대표 쟁점 선정.
3. 구현: 공통 자산·행동 규격 → 한 장면 재생기 → AI 장면 지시 검증.
4. 구현: 근거 연결·반문·주장 수정 → 사용자 선택 흐름.
5. 확장: 나머지 제품군과 기본 장면 연결.
6. 함께: 클릭 프로토타입 UT → 수정 → 실제 AI MVP 검증.

피터 담당: 서비스 의도·우선순위·디자인 판단·사용자 모집 및 실제 피드백.
AI 지원: 요구사항·화면 및 데이터 규격·코드·도트 자산 제작 지원·검증 시나리오·결과 정리.

## 14. 미확정 사항

도트 시점(측면/탑뷰), 캐릭터 비율, 최종 4종, 제품 링크 지원 사이트, 대상 화면 크기, 개발 기간, 무료 API 실제 한도, 근거 자료 확보 방식. 무료 API의 존재만으로 공개 서비스의 무제한 운영을 보장하지 않는다.
